## Contract: anything that is wrong or that you could not meet (with evidence), else "met"
Host side: **met**, with these notes.

- §1: the prediction is exact for the full-screen case (window minus cutout insets minus the extra-key bar), nothing is rounded to even, and `OMARCHY_OUTPUT_*` is exported only when both dimensions are > 0 (unit-tested). The bar height uses Termux:X11's own formula (`round(37.5 * density * rows)`).
- §2: the wait rule is the pure `LaunchReadiness.decide`. The fallback's 25 s is measured from the first moment the launcher observes a `hypr/<instance>` directory (not its mtime, which Hyprland can touch again), gives up at once when `ProotService.isRunning()` is false, and the hard cap is 120 s.
- §5: session start order is prep (launcher) → X server → proot; no host compositor is started any more. The ready marker is removed by `SessionPrep` when it wipes `omarchy-runtime`.
- §6: host lines are `Phoshdroid` / `launch: <phase> <ms>ms`, ms since the launcher object was created.
- Deviation to flag: on TIMEOUT or SESSION_DIED the host still hands over to MainActivity (it only logs `desktop not ready (<REASON>); handing over anyway`). That is the pre-existing behaviour and avoids leaving the user on a dead loading screen, but it is not literally "give up". Making it stay on the error screen is a one-line change if the contract wants that.

## Device checklist for the parent
1. **Cold start is ready only when drawn.** `adb logcat -s Phoshdroid` must show, in this order: `launch: prefix-extracted ...ms`, `launch: rootfs-extracted ...ms`, `launch: x11-socket exists=true ...ms`, `launch: session-started ...ms`, `launch: ready marker ...ms`, `launch: handover done ...ms`. The `ready` phase must be seconds after `session-started` (about 9 s on the tablet), never 0–1 ms; an immediate `ready` means a stale marker survived.
2. **No Settings page on the launch path.** From a cold start the launcher must go straight to the desktop, every time, with no Settings screen in between. In Settings, switching **Mount /sdcard** on while the app has no all-files access must open the system "All files access" page; switching it on again after granting must open nothing.
3. **Geometry on the tablet.** The X root must be 3200x1971 and start at the top row of the window, with the 165 px extra-key bar directly below it: check the guest's `/tmp/fit-x11.log` / watcher log for `3200x1971`, or `docs/omarchy/tools/probe.sh` naming that root. There must be **no ~140 px black band above the bar** (the old top gap + centre gravity put the view at row 140), and the bar must not cover the desktop.
4. **Live size change without a restart.** Rotate or fold/unfold while the desktop runs: `docs/omarchy/tools/probe.sh` must print `VERDICT: PASS` within 15 s, the open windows must still be open, logcat must show `<Activity> ... display shift ... recording`, and the process must not die (no second `Launching X11 activity...`, no new `launch: prefix-extracted`).
5. **Old guest image fallback.** With a guest that writes no `omarchy-ready`, the hand-over must still happen, logged as `launch: ready fallback`, about 25 s after `hypr/<instance>` first appears; with no instance dir at all it stops at `launch: ready timeout` (120 s) and still shows the display activity.
6. **A sticky restart cannot start a blind guest.** With the desktop running, `adb shell am kill com.phoshdroid.app`: the notification must disappear and logcat must show `ProotService ... null intent (system restart of a sticky service); stopping instead of starting a session`; no proot process may be spawned.

## Not done / risks
- **The submodule has an uncommitted hunk**: `termux-x11/app/src/main/java/com/termux/x11/MainActivity.java` (12 insertions, 5 deletions) is part of this change and must be committed in the submodule with the app commit. Without it, margins apply to a centred view and the X view does not sit at row 0.
- **Old guest image (no ready marker)**: the hand-over waits the 25 s fallback after the instance dir appears, so a cold start against a stale guest image spends ~25 s longer on the splash than the marker path. Per the contract, but observable as "slow".
- **Timeout still hands over**: on `timeout`/`session-died` the display activity is started anyway (with a warning) rather than leaving the user on the loading screen. Contract §2 says "give up"; say if that should mean no hand-over.
- **H3 deferral paths**: `onResume` and `onNewIntent` both complete a deferred hand-over, and a launch-path failure blocks it via `bootstrapFailed`. Not exercisable on a device: a resume arriving while `bootstrapInProgress` is still true leaves the hand-over to the next resume (the bootstrap's own RESUMED check usually catches it). Reasoning, not observation.
- **H4 with the switch false**: if the guest fails to follow a live X root, the desktop will be letterboxed/cut until someone flips `RESTART_SESSION_ON_DISPLAY_SHIFT`. The old restart path is intact behind it.
- **Extra-key rows on the first launch**: `TermuxX11ExtraKeys.getExtraKeysInfo()` reads `MainActivity.getPrefs()`, which is null until `MainActivity.onCreate`, so a fresh process falls back to 2 rows. A user with a custom extra-keys config of a different row count gets the wrong bottom gap on that launch (the bar covers or under-covers the desktop by one row's height). Reading the `extra_keys_config` pref JSON directly would fix it; out of scope here.
- **Scale is resolved once per session start** (the service receives an integer), so a rotation does not change the scale until the next launch. By design (contract §4 is per session), but visible.
